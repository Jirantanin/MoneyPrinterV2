# ให้มิ้งมองภาพที่ตัวเองวาด ก่อนหาเครื่องมือใหม่

คำตอบสั้นคือ งานวิจัยปี 2025–2026 ชี้ไปทางเดียวกันหมดว่า ภาพ SVG ที่ LLM วาดจะดีขึ้นจริงเมื่อเปลี่ยน **กระบวนการ** ไม่ใช่เปลี่ยนโมเดลหรือเพิ่มแอป เพราะ frontier model ทั้ง Claude, GPT และ Gemini คะแนน text-to-SVG ห่างกันแค่ราว 1.5 คะแนน ส่วนระบบที่ชนะ benchmark ล้วนมีสามอย่างเหมือนกัน คือ render ออกมาแล้วป้อนภาพกลับให้โมเดลดู, บังคับให้วาดจาก primitive ง่าย ๆ แล้วค่อยเกลารูปทรงทีหลัง, และใช้ตัวตัดสินแยกที่มีสัญญาณจากภายนอก จุดอ่อนสี่ข้อของมิ้งตรงกับจุดอ่อนที่มีเอกสารยืนยันพอดี LLM เขียน path ซับซ้อนแบบ organic ได้ไม่ดีและจัด layout ได้ไม่แม่น ส่วน VLM ก็ดูภาพพลาดตรงที่รูปทรงซ้อนกัน อยู่ชิดกัน หรือต้องนับจำนวน ซึ่งก็คือมือ นิ้ว และขอบที่เกือบชนกัน ดังนั้นการให้ reviewer subagent ดูแค่ภาพเต็มเฟรมจึงจับปัญหาที่สำคัญที่สุดไม่ได้ แผนที่คุ้มที่สุดสำหรับ pipeline นี้ เรียงตามผลต่อแรง คือ (1) ให้คนวาดดูภาพที่ render จริงพร้อมภาพ crop เฉพาะส่วน วนไม่เกิน 2–3 รอบ (2) เพิ่ม lint เชิงเรขาคณิตใน `gfx_kit` ให้ตรวจสิ่งที่ VLM มองไม่เห็น (3) ยกระดับ reviewer ให้มี rubric, crop, style frame และตัวอย่างจากตอนเก่า (4) เปลี่ยนการวาดตัวละครจากวาดใหม่ทุกท่า เป็น rig แบบ JSON ที่วาดชิ้นส่วนครั้งเดียวแล้วจัดท่าด้วยการหมุนตัวเลข (5) ขยายเครื่องมือสร้างรูปทรง organic แบบ `rock()` ให้ครอบคลุมสัตว์ พืช และเมฆ ส่วน EffectCraft, VectorCraft, Figma, Blender และ image generator อยู่ท้ายรายการ ผลทดลอง EffectCraft ที่ได้แค่ "ดีขึ้นนิดหน่อย" ตรงกับหลักฐานพอดี เพราะ post-pass แต่งได้แค่ผิว แก้การวาดที่ผิดตั้งแต่โครงไม่ได้

## เปลี่ยนโมเดลได้ไม่ถึง 2 คะแนน แต่การดูภาพ render ลด FID ได้ 9–21%

benchmark ใหม่ที่สุดที่ทดสอบโมเดลรุ่นปัจจุบันคือ VectorGym (2026) ผลด้าน Text2SVG ได้ **GPT-5.1 70.68, Gemini 3 Pro 69.92, Claude Sonnet 4.5 69.19** แต่ละโมเดลชนะกันคนละงาน Claude Sonnet 4.5 ทำ SVG editing ได้ DINO สูงสุด (95.61) และ MSE ต่ำสุด (6.29) ([VectorGym](https://arxiv.org/html/2603.29852v1)) งานแก้ไขแบบนี้ใกล้กับงานที่มิ้งทำใน `scenes.js` ทุกวันมากกว่าการวาดจากศูนย์ ใน SVGenius ซึ่งแบ่งระดับความยาก Claude-3.7-Sonnet ได้ rCLIP 87.97 บน Hard prompt ทิ้ง GPT-4o (82.81) และโมเดลเฉพาะทางอย่าง IconShop (72.55) กับ LLM4SVG (62.98) ที่พังเมื่อโจทย์ยากขึ้น ([SVGenius](https://arxiv.org/html/2506.03139)) สรุปได้ว่าโมเดลที่มิ้งใช้อยู่ไม่ได้เป็นคอขวด และ benchmark เหล่านี้วัดว่า "ดูออกไหมว่าเป็นอะไร" (CLIP, HPS) มากกว่าความงาม คะแนนนำจึงไม่ได้แปลว่าได้งานระดับ Kurzgesagt

สิ่งที่ทำให้คุณภาพขยับจริงคือการป้อนภาพที่ render แล้วกลับเข้าโมเดล IntroSVG ทดลองวน generate → render → critique → refine แบบ zero-shot กับโมเดลทั่วไป **FID ของ GPT-5 ลดจาก 35.87 เหลือ 32.68 และของ Grok-4 ลดจาก 41.39 เหลือ 32.85 ใน 3 รอบ** แต่กราฟไม่ได้ขึ้นเรื่อย ๆ CLIP ของ GPT-5 สูงสุดที่รอบ 1–2 แล้วตกลงมา และ HPS ของ Grok-4 ไม่ขยับเลย กฎหยุดที่งานนี้ใช้คือไม่เกิน 3 รอบ หรือหยุดเมื่อ critic ให้คะแนน ≥ 9.5 ([IntroSVG](https://arxiv.org/html/2603.09312v1)) RLRF (NeurIPS 2025) อธิบายสาเหตุตรง ๆ ว่าโมเดลที่ฝึกแค่ SFT ล้มเหลวเพราะ "fail to incorporate visual feedback from rendered outputs" จึงหลอนหรือวนลูปเมื่อต้องเขียน SVG ยาว ([RLRF](https://arxiv.org/html/2505.20793v2)) ถ้ามิ้งเขียน scene code แล้วส่งต่อให้ reviewer โดยไม่เคยเปิดดู PNG เอง มิ้งก็อยู่ในสถานะเดียวกับโมเดลที่งานพวกนี้พยายามแก้

Chat2SVG (CVPR 2025) ใช้ **claude-3-5-sonnet** เป็นแกน และเป็นแม่แบบที่ลอกมาใช้ได้ตรงที่สุด ขั้นแรก LLM แตกฉากเป็นวัตถุหลัก วัตถุเสริม และชิ้นส่วนของแต่ละวัตถุ พร้อมระบุตำแหน่ง ขนาด สี และการซ้อนทับ จากนั้นเขียน SVG ด้วย rect, ellipse, line, polyline, polygon และ path สั้น ๆ เท่านั้น ทุกชิ้นมี id และ comment ระบุว่าเป็นส่วนไหน ขั้นที่สองคือ "visual rectification" ป้อนภาพกลับไปให้หาชิ้นที่วางเหลื่อม ชิ้นที่ถูกบัง วัตถุที่ดูไม่ออก สัดส่วนเพี้ยน และลำดับชั้นผิด ราว 2 รอบก็พอ เหตุผลที่จำกัด primitive คือ LLM "has limitations in synthesizing geometrically complex paths" และ "may produce imprecise visual layouts" รายละเอียด organic จึงย้ายไปให้ optimizer ทำในขั้นที่สาม ([Chat2SVG](https://arxiv.org/html/2411.16602v1)) ผลรวมของ pipeline นี้ชนะ SVGDreamer ด้าน Path FID (39.07 ต่อ 47.95) แต่ข้อจำกัดที่ต้องพูดตรง ๆ คือยังไม่มีงานไหนแยกวัดผลของ "plan ก่อนเขียน" หรือ "reasoning ก่อนเขียน" แบบ prompt อย่างเดียวกับ frontier model หลักฐานที่มีมาจากการฝึกโมเดล เช่น Reason-SVG และ SVGThinker ([Reason-SVG](https://arxiv.org/html/2505.24499v1); [SVGThinker](https://arxiv.org/html/2509.24299v1)) ขีดจำกัดอีกข้อคือทุกโมเดลแย่ลงเมื่อ SVG ยาวขึ้น และทำตามคำสั่งแก้หลายขั้นต่อกันได้ไม่ดี ([VectorGym](https://arxiv.org/html/2603.29852v1)) จึงควรเขียนทีละ `<g>` แล้วประกอบ ไม่ควรเขียนทั้งฉากในก้อนเดียว

## VLM แม่นแค่ราว 58% บนโจทย์ที่เด็กทำได้ ภาพเต็มเฟรมจึงไม่พอ

ปัญหาของ reviewer subagent ชุดปัจจุบันไม่ได้อยู่ที่ความขยัน แต่อยู่ที่ตา งาน "Vision language models are blind" ให้ VLM ระดับ SOTA ทำโจทย์ง่ายเจ็ดแบบ เช่น เส้นตัดกันไหม วงกลมซ้อนกันไหม นับจำนวน **ได้เฉลี่ยราว 58% ตัวที่ดีที่สุดคือ Claude 3.5 Sonnet ราว 74–78% ขณะที่คนได้ 100%** โมเดลพลาดหนักที่สุดเมื่อรูปทรงซ้อนหรืออยู่ชิดกัน และเกือบถูกหมดเมื่อรูปทรงอยู่ห่างกัน การทำภาพให้เรียบง่ายขึ้นเพิ่มความแม่นในการนับรูปที่ซ้อนกันของ Sonnet-3 ได้ถึง 63 จุด ที่น่าสนใจคือ linear probe บน vision encoder ทำได้ ≥ 99.47% แปลว่าข้อมูลอยู่ในภาพครบ แต่หายไปตอนแปลงเป็นคำตอบ ([VLMs are blind](https://arxiv.org/html/2407.06581v4)) นิ้วมือ ข้อศอกที่ทับลำตัว และป้ายที่เกือบแตะขอบวงแหวน คือโจทย์แบบนี้ทั้งหมด

ทางแก้มีหลักฐานรองรับสองทาง ทางแรกคือการ crop งาน "MLLMs Know Where to Look" (ICLR 2025) พบว่าความแม่นของ MLLM ขึ้นกับขนาดของวัตถุในภาพโดยตรง โมเดลมองถูกตำแหน่งแม้จะตอบผิด การป้อนภาพเต็มคู่กับภาพ crop เฉพาะส่วนให้ผลดีขึ้นชัดเจนบนเจ็ด benchmark โดยไม่ต้องฝึกเพิ่ม ([ViCrop](https://arxiv.org/html/2502.17422v1)) ทางที่สองคือย้ายคำถามเชิงเรขาคณิตไปให้โค้ดตอบ อย่าให้ VLM เดา VectorGym ยังพบว่า VLM judge "more permissive than humans" และให้คะแนนกลาง ๆ เมื่อไม่แน่ใจ ([VectorGym](https://arxiv.org/html/2603.29852v1)) การถาม reviewer ว่า "ให้คะแนนเฟรมนี้ 1–10" จึงได้ข้อมูลน้อยที่สุด

เรื่องที่ซับซ้อนกว่าคือการให้ตัวเองตรวจตัวเอง Huang et al. (ICLR 2024) พบว่าโมเดล "cannot inherently correct their own reasoning errors without external feedback" และมักแก้คำตอบที่ถูกให้กลายเป็นผิด ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)) ส่วน LLM judge ก็ให้คะแนนงานตัวเองสูงกว่าที่คนให้ และ bias นี้แรงขึ้นตามความสามารถในการจำงานตัวเองได้ ([arXiv 2404.13076](https://arxiv.org/html/2404.13076v1)) ความหมายในทางปฏิบัติคือ loop ใช้ได้ต่อเมื่อแต่ละรอบมีสัญญาณใหม่เข้ามา เช่น ภาพ render ใหม่ ผล lint หรือ judge ที่ context สะอาด งาน "See it. Say it. Sorted." วางโครงไว้ดี critic VLM เสนอแก้ไม่กี่ข้อในรูปความสัมพันธ์ ("ขยับดาวให้ซ้อนดวงจันทร์") แทนตัวเลขพิกัด, LLM หลายตัวลงมือแก้คนละสไตล์, แล้ว judge VLM อีกตัวเลือกผลที่ดีที่สุด แต่ทดสอบแค่ 10 ภาพร่าง จึงยังเป็นหลักฐานบาง ๆ ([arXiv 2508.15222](https://arxiv.org/abs/2508.15222v2)) หลักฐานที่หนักกว่าคือ UICrit ซึ่งพบว่า **few-shot ด้วยคำวิจารณ์จากนักออกแบบตัวจริงร่วมกับ visual prompting ทำให้ feedback ที่ LLM สร้างดีขึ้น 55%** ([UICrit](https://arxiv.org/abs/2407.08850)) แต่ PerceptUI (2026) ก็ยังพบว่าคำวิจารณ์ของนักออกแบบคนจริงนำทุกวิธีของ LLM อยู่ที่ 0.75 ต่อ 0.48 ([PerceptUI](https://arxiv.org/pdf/2606.05697)) ตรงนี้คือเหตุผลที่นนยังต้องเป็นคนตัดสินคนสุดท้าย

ตาราง rubric ข้างล่างแบ่งงานระหว่างโค้ดกับ VLM ตามหลักฐานข้างบน นิยามของ tangent มาจากแหล่งด้านการวาดภาพประกอบ คือขอบที่ "not either overlapped or given some space between them" ทำให้ความลึกสับสน ([The Informed Illustrator](https://www.theinformedillustrator.com/2013/10/off-on-tangent.html)) ส่วน safe zone ของ Shorts ไม่มีสเปกทางการจาก YouTube ตัวเลขจากแหล่ง third-party คือบนราว 15% ล่างราว 15% และขวาราว 140 px ของเฟรม 1080×1920 ([Clipspeed](https://www.clipspeed.ai/blog/youtube-shorts-size.html)) ขณะที่อีกแหล่งเสนอพื้นที่กลางราว 900×1400 px และเตือนเองว่าไม่ใช่สเปกทางการ ([Reap](https://reap.video/blog/short-form-video-safe-zones)) ค่า threshold ในตารางเป็นค่าตั้งต้นที่มิ้งเสนอ ยังต้องจูนกับตอนเก่า

| ข้อตรวจ | ใครตรวจ | วิธี / เกณฑ์ตั้งต้น |
|---|---|---|
| Tangent (ขอบเกือบชน) | โค้ด | ระยะต่ำสุดระหว่าง outline ของทุกคู่ `<g>` ที่มี id และระหว่าง outline กับขอบเฟรม ต้องซ้อนชัดหรือห่างชัด ถ้าอยู่ในช่วง ±6–10 px ที่ 1080p ให้ fail |
| Safe zone 9:16 | โค้ด | text และ focal subject อยู่ใน x∈[60, 940], y∈[290, 1550] |
| Palette | โค้ด | ไม่มี hex ดิบใน scene ใช้แต่ token จาก `theme()` |
| Silhouette | โค้ด + VLM | render แบบเติมดำทั้งตัว แล้วถาม VLM ว่าท่าอ่านออกไหม |
| จำนวนนิ้ว / ชิ้นที่ซ้ำ | โค้ด | นับจาก id ใน DOM ไม่ใช่จากภาพ |
| Focal point เดียว อ่านออกในหนึ่งวินาที | VLM | ภาพเต็มย่อเล็ก (squint test) |
| มือ หน้า ป้าย | VLM | crop 2–4 จุด ถามเป็นคำถามใช่/ไม่ใช่ |
| ตรงกับคำบรรยาย ณ วินาทีนั้น | VLM | ส่งประโยค narration ไปพร้อมเฟรม |
| สไตล์ตรงกับ style frame | VLM | วางเทียบข้างกับ style frame ที่นนอนุมัติแล้ว |

## มือกับท่าทางต้องเป็นตัวเลข ไม่ใช่ลายเส้น

จุดอ่อนเรื่องกายวิภาคของมิ้งแก้ได้ด้วยการเปลี่ยนโจทย์ ไม่ต้องฝึกวาดให้เก่งขึ้น สตูดิโอเองก็ไม่ได้วาดใหม่ทุกท่า Kurzgesagt แยกภาพประกอบเป็นชิ้น rig ตัวละครทุกตัวใน After Effects และบอกว่า "Every single thing that's moving on-screen has been moved manually" ([LingQ mirror ของ transcript Kurzgesagt](https://www.lingq.com/en/learn-english-online/courses/689474/how-to-make-a-kurzgesagt-video-in-120-4887128/)) ฝั่ง After Effects ใช้ Joysticks 'n Sliders ซึ่ง key ท่าสุดขั้วห้าท่าแล้ว interpolate ระหว่างกัน สำหรับกะพริบตา มองซ้ายขวา รูปปาก ท่ามือ และหันหัว ([aescripts](https://aescripts.com/joystick-n-sliders); [Udemy](https://www.udemy.com/course/rigging-and-animating-psds-with-duik-joysticks-n-sliders/))

รูปแบบที่ใช้กับโค้ดได้ตรงที่สุดคือ character-rigging skill ของ OpenMontage ให้ runtime เป็นโค้ดกลาง แล้วเก็บตัวละครแต่ละตัวเป็น data package แบบ JSON มี `parts` (id, layer, parent) และ `joints` (pivot ในพิกัด artwork พร้อมช่วงหมุน เช่นหัว `[-20, 20]`) กฎของ skill นี้คือ แยกตา รูม่านตา และปากเป็นชิ้นต่างหาก, แยก prop ที่ตัวละครถือเป็นชิ้นต่างหาก, กำหนด pivot เป็นพิกัด SVG ชัดเจนเพราะพฤติกรรมของ `transform-origin` ขึ้นกับ browser, กำหนด layer เองโดยไม่พึ่งลำดับใน source และให้ animation เป็น frame-driven แบบ deterministic ([skills.cat: openmontage/character-rigging](https://skills.cat/skills/calesthio/openmontage/character-rigging)) ข้อสุดท้ายเข้ากับ `record.cjs` ที่อัดเฟรมด้วย puppeteer อยู่แล้ว ข้อดีหลักคือมิ้งวาดชิ้นส่วนครั้งเดียวในท่ายืนตรง จากนั้นทุกท่าคือชุดมุมหมุน และ joint limit จะกันท่าที่ข้อต่อหักผิดทาง ปัญหาการวาดกลายเป็นปัญหาตัวเลขที่ LLM ถนัด

กฎการสร้างตัวละครที่เขียนลงโค้ดได้มีแหล่งรองรับระดับพอใช้ ตัวละครแบบ stylised สูง 2–4 หัว เทียบกับคนจริง 7–8 หัว แขนขาเป็นทรงกระบอกเรียวที่ไม่มีกล้ามเนื้อ มือย่อเป็นถุงมือ หรือแยกเป็นสองชิ้นคือนิ้วโป้งกับก้อนสี่นิ้ว ([Clip Studio Tips](https://tips.clip-studio.com/es-es/articles/4879?org=1); [Clip Studio: chibi](https://tips.clip-studio.com/ja-jp/articles/4897?org=1)) สำหรับ pipeline นี้หมายความว่า มือเป็น capsule หนึ่งชิ้นบวกนิ้วโป้งหนึ่งชิ้นเสมอ เพิ่มนิ้วเป็น capsule ก็ต่อเมื่อท่าต้องใช้ เช่นชี้ แขนขาเป็น stroke `stroke-linecap: round` ระหว่างจุดข้อต่อ ซึ่งซ่อนความผิดพลาดตรงข้อศอกได้ และใช้ชุดท่าปิด (ยืน เดิน ชี้ ยักไหล่ นั่ง ตกใจ) แทนการคิดท่าใหม่ทุกช็อต ถ้าอยากได้ท่าที่ถูกกายวิภาค ให้ดึง landmark จาก MediaPipe Pose (`@mediapipe/tasks-vision`) บนภาพอ้างอิงครั้งเดียว แล้วแปลงเป็นมุมข้อต่อเก็บไว้ใน pose library ([Google AI Edge](https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker/web_js?authuser=8)) วิธีนี้ยืมไอเดีย retarget ของ Meta Animated Drawings มาใช้โดยไม่ต้องลากตัวระบบมาด้วย ตัว Animated Drawings เองถูก archive ไปตั้งแต่กันยายน 2025 และทดสอบแค่บน macOS กับ Ubuntu ([AnimatedDrawings](https://github.com/facebookresearch/AnimatedDrawings)) ซึ่งไม่เข้ากับเครื่องนนที่ไม่ใช้ WSL

ต้องดู `LIBRARY.md` ประกอบด้วย กฎของนนคือห้ามหยิบ prop หรือตัวละครประจำหัวข้อจากตอนก่อนมาใช้ซ้ำ rig จึงต้องแยกเป็นสองชั้น ตัว runtime (pivot, pose interpolation, joint limit) อยู่ในชั้น "tools the viewer never sees" ของ `kit.js` ส่วนชิ้นส่วนและ JSON ของตัวละครแต่ละตัววาดใหม่ในแต่ละตอน ข้อนี้ตรงกับที่ Kurzgesagt มี library แต่ก็ยังวาดภาพส่วนใหญ่ใหม่จากศูนย์ ([LingQ](https://www.lingq.com/en/learn-english-online/courses/689474/how-to-make-a-kurzgesagt-video-in-120-4887128/))

สำหรับรูปทรง organic บทเรียนจาก Chat2SVG ใช้ได้ตรง ๆ คือให้ LLM วางโครงจาก primitive แล้วให้ procedure สร้างความเป็น organic `library.js` มี `rock()` ที่สร้างหินหรืออุกกาบาตจาก seed อยู่แล้ว ซึ่งเป็นแนวเดียวกับวิธีที่มีแหล่งอ้างอิง คือดันจุดบนวงกลมออกตามค่า noise ([Babylon.js forum](https://forum.babylonjs.com/t/procedural-rock-generator-any-ideas/9568)) เกม dev ยังพบว่าการเอารูปทรงต้นแบบหลายแบบมาบิดด้วย noise ได้ความหลากหลายดีกว่าการจูน noise อย่างเดียว ([Unity discussions](https://discussions.unity.com/t/procedural-asteroid-generation/639383)) ทางขยายที่ควรทำคือ superformula สำหรับใบไม้ กลีบดอก และปลาดาว ([SIGGRAPH history](https://history.siggraph.org/?p=99344)), perfect-freehand (MIT) สำหรับหาง ก้าน หนวด และหญ้าที่เรียวปลาย ([perfect-freehand](https://github.com/steveruizok/perfect-freehand)) และเมฆหรือก้อน blob จากวงกลมหลายวงรวมกัน ส่วนสัตว์ให้ประกอบจาก ellipse ลำตัว วงกลมหัว และสามเหลี่ยมหูหรือจะงอยปาก ([cartoon bird construction](https://appmgss.impactfirst.co/post/how-to-draw-a-cartoon-bird)) โดยแยกชิ้นไว้ให้ rig ได้ เรื่องที่ยังไม่มีหลักฐานคือ ไม่พบ tutorial ที่สอนวิธีนี้กับ SVG โดยตรง ทั้งหมดดัดแปลงจากแหล่ง 3D และเกม

## art direction ต้องบังคับในโค้ด ไม่ใช่แค่เขียนบอก

ต้นเหตุของงานที่ "ดูเหมือน AI" ถูกอธิบายไว้ในบล็อกของ Anthropic เอง เมื่อไม่มีการกำกับ โมเดลจะสุ่มจาก "high-probability center" ของข้อมูลฝึก ทางแก้คือ skill ราว **400 token** ที่โหลดเฉพาะตอนทำงานออกแบบ เลือกทิศทางที่ชัดหนึ่งทางต่อแต่ละมิติ และตั้งกฎให้วัดได้ เช่น ใช้น้ำหนักฟอนต์แบบสุดขั้ว 100/200 คู่กับ 800/900 และขนาดกระโดด 3 เท่าขึ้นไป พร้อมเตือนไม่ให้ไปติดค่า default ชุดใหม่ ([Claude blog](https://www.claude.com/blog/improving-frontend-design-through-skills)) หลักฐานของบทความนี้เป็นภาพเทียบก่อนหลังเท่านั้น ไม่มีตัวเลข ส่วน DESIGN.md ของ Google Stitch มีรีวิวว่าเปลี่ยนฟอนต์หัวเรื่องแล้วไม่ไปถึงทุกจุด ([Tutorials Dojo](https://tutorialsdojo.com/what-google-stitch-actually-does-and-where-it-falls-short/)) บทเรียนสำหรับ repo นี้คือ token ต้องบังคับผ่าน `theme()` และ lint ที่ fail เมื่อเจอ hex ดิบ การเขียนเป็นร้อยแก้วอย่างเดียวไม่พอ

ฝั่งสตูดิโอให้สองขั้นตอนที่ pipeline นี้ยังไม่มี ขั้นแรกคือ style frame ภาพนิ่งที่ทุกคนตกลงกันก่อนเริ่มผลิตจริง และใช้เป็นภาพอ้างอิงตลอดงาน ([Milanote](https://www.milanote.com/guide/motion-design-style-frames)) ขั้นที่สองคือ color script แบบ Pixar ที่ Ralph Eggleston ทำภาพสีเล็ก ๆ ของทุกฉากเพื่อดูว่าความเข้มของสีเดินตามอารมณ์เรื่อง ([MoMA](https://www.moma.org/audio/playlist/192/2581)) Kurzgesagt เองร่าง visual metaphor และจัดลำดับว่าฉากไหนต้องทุ่มแรงที่สุดก่อนลงมือวาด ใช้ภาพราว 200 panel ต่อวิดีโอ และรีวิวกัน "every few days" ([LingQ](https://www.lingq.com/en/learn-english-online/courses/689474/how-to-make-a-kurzgesagt-video-in-120-4887128/)) สำหรับมิ้ง style frame ที่นนอนุมัติแล้วยังมีประโยชน์เพิ่มอีกข้อ คือเป็นภาพเทียบให้ reviewer ใช้แทนคำถามว่า "สวยไหม" ซึ่งลด self-preference bias ได้ตามที่กล่าวไว้ในหัวข้อที่สอง

### แผนแปดข้อ เรียงตามผลต่อแรงสำหรับ pipeline นี้

| อันดับ | ทำอะไร | ผูกกับส่วนไหนของ pipeline | หลักฐาน | แรงที่ต้องลง |
|---|---|---|---|---|

| 2 | lint เชิงเรขาคณิต ได้แก่ tangent, safe zone, hex ดิบ, bbox ล้นเฟรม, นับชิ้นจาก id และ silhouette mask | สคริปต์ Node ที่ใช้ puppeteer เปิด `template.html` แล้วอ่าน `getBBox()` ของทุก `<g id>` | VLMs are blind, Informed Illustrator | ต่ำถึงกลาง |

| 7 | ภาพอ้างอิงแบบ raster ใช้แปลงเป็นสเปกสัดส่วนและท่าทาง (มุมข้อต่อ) ไม่ใช้ trace เป็นงานจริง | ขั้น research ของแต่ละตอน | RLRF Im2SVG SSIM ราว 60–70 | ต่ำ |
| 8 | ทดลอง Recraft บน paid plan เฉพาะ prop หรือพื้นหลัง ส่วน VectorCraft ใช้เฉพาะ boolean op และหยุดลงแรงกับ EffectCraft post-pass | นอก pipeline หลัก | หลักฐานคุณภาพยังไม่มี | ต่ำ (ใช้เงิน) |

ข้อ 1–3 ทำได้ในสัปดาห์เดียวและแก้จุดอ่อนเรื่อง "ตัดสินงานตัวเองไม่ได้" ตรง ๆ ข้อ 4–5 แก้เรื่องกายวิภาคและรูปทรง organic แต่ต้องลงทุนเขียนโค้ดก่อน ควรเริ่มจากตัวละครหนึ่งตัวในตอนถัดไปแล้ววัดผลกับนน ข้อ 6 สำคัญเรื่องการจัดภาพ แต่ตามกฎใน CLAUDE.md มิ้งสร้าง skill เองไม่ได้ นนต้องเป็นคนสั่ง

## Conclusion

ข้อค้นพบที่เปลี่ยนวิธีคิดมากที่สุดคือ คอขวดของ pipeline นี้ไม่ใช่ฝีมือการวาดของโมเดล แต่เป็นตำแหน่งของตา ตอนนี้สายตาไปอยู่ที่ reviewer ปลายทางซึ่งดูภาพเต็มเฟรม และเป็นจุดที่ VLM มองพลาดมากที่สุด ทั้งที่หลักฐานบอกว่าคนวาดควรเป็นคนดูภาพ render ของตัวเอง ดูทีละส่วน และส่งคำถามเชิงเรขาคณิตให้โค้ดตอบ ผลทดลอง EffectCraft ที่ได้แค่ "ดีขึ้นนิดหน่อย" จึงไม่ได้แปลว่าเลือกเครื่องมือผิดตัว แต่แปลว่าทุกเครื่องมือที่ทำงานหลังการวาดมีเพดานเท่ากันหมด เพราะแก้โครงที่ผิดไม่ได้

สิ่งที่ยังไม่รู้และควรวัดเองคือ ยังไม่มี benchmark ไหนทดสอบ Claude รุ่น Opus หรือรุ่นปัจจุบันในฐานะ critic ของ SVG ตัวเอง ไม่มีตัวเลขความผิดพลาดแยกตามประเภท (มือ สัตว์ มุมมอง) และค่า threshold ทุกตัวในแผนเป็นค่าตั้งต้น ทางที่ถูกจึงเป็นการเก็บข้อมูลจากช่องเอง ให้ทุกครั้งที่นนติเฟรมกลายเป็นตัวอย่าง few-shot ของ reviewer และกลายเป็น lint rule เมื่อทำได้ เมื่อเวลาผ่านไป มาตรฐานของนนจะถูกเขียนลงเป็นโค้ดทีละข้อ ช่องว่าง 0.75 ต่อ 0.48 ระหว่างนักออกแบบคนจริงกับ LLM ใน PerceptUI บอกว่าเครื่องมือสำเร็จรูปปิดช่องนี้ไม่ได้ สิ่งที่ปิดได้คือคำวิจารณ์ของคนจริงที่ถูกเก็บสะสมไว้ใช้ซ้ำ
